fix(winreg): decode registry names/values as WTF-8; accept surrogate strings

test_mimetypes failed on Windows: the registry (HKEY_CLASSES_ROOT) contains
keys whose names include lone surrogates, and `_winreg.EnumKey` decoded
UTF-16 with a strict `String::from_utf16`, raising
`ValueError: UTF16 error: invalid utf-16: lone surrogate found`. After
fixing that, the same test hit a second issue: winreg functions took
`String` parameters, which are converted by downcasting the argument to
PyUtf8Str — a payload variant that only accepts valid-UTF-8 strings, so any
surrogate-containing key name failed with
`RuntimeError: Expected payload 'str' but 'str' found` in
`_winreg.OpenKey`.

Both are fixed the way CPython handles them (PyUnicode_FromWideChar /
PyUnicode_AsWideChar round-trip arbitrary UTF-16 code units):

- EnumKey/EnumValue/QueryValueEx decode to WTF-8 (Wtf8Buf::from_wide), so
  lone surrogates survive in the Python str; REG_SZ / REG_MULTI_SZ values
  get the same treatment.
- All winreg parameters that name registry keys, values, files or
  computers switched from `String` to `PyStrRef`, converted to wide chars
  via `as_wtf8().to_wide*()`; the OsStr-taking host calls use
  `OsString::from_wide`, preserving surrogates end to end.

Verified: test_mimetypes 38 run green (previously 1 error), test_winreg 25
run green. Regression: test_importlib 1,440, test_ctypes 328, test_sysconfig
37, test_venv 40, test_signal 57, test_threading 229 all green; pyd smoke
passes; clippy clean (no new warnings).
