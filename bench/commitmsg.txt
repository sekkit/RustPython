feat: CPython-exact SOABI extension suffix; pip binary wheels install and import

Extensions were named "<name>.pyd" with sysconfig SOABI="" and
EXT_SUFFIX=".pyd", so pip's ABI tag derivation and the FileFinder's suffix
list could never agree with a real wheel layout: a wheel whose .pyd carries
the SOABI suffix would not be importable, and "cp314"-tagged wheels did not
match the interpreter's supported tags at all.

Now everything is CPython-exact:

- version.rs: SOABI = "cp" + major + minor + "-win_amd64" ("cp314-win_amd64"),
  mirroring CPython's PC/pyconfig.h definition.
- _imp.extension_suffixes() returns [".cp314-win_amd64.pyd"] so the FileFinder
  only matches SOABI-named extensions (CPython 3.14 behavior; the importlib
  extension test util scans sys.path with these suffixes).
- _sysconfig: SOABI="cp314-win_amd64", EXT_SUFFIX=".cp314-win_amd64.pyd"
  (test_sysconfig asserts EXT_SUFFIX == extension_suffixes()[0] and
  SOABI in extension_suffixes()[0]).
- bench/build_test_extensions.ps1 emits Lib\_testsinglephase.cp314-win_amd64.pyd
  and Lib\_testmultiphase.cp314-win_amd64.pyd.
- bench/wheel_demo/: reproducible binary-wheel demo (spam.c, wheel builder,
  README). The wheel tag is "rustpython314-cp314-win_amd64": packaging.tags
  derives the interpreter part from sys.implementation.name ("rustpython314")
  and the ABI part from SOABI ("cp314"). Real CPython cp314 wheels are
  rejected by pip, which is deliberate — only extensions built against the
  python314 shim ABI can load.

Verified end to end: pip install of the demo wheel into site-packages and
import of the installed .pyd (spam.hello/add, importlib.metadata.version),
pip uninstall/reinstall, and pip install six from PyPI. Regression:
test_importlib 1440 run green, test_ctypes 328 green, test_sysconfig 37
green, pyd smoke all pass, capi cargo test 112 pass, clippy clean.
